# 车端重启后的 App 自动恢复修复

2026-10-03。GL 无线周期性停顿仍存在，整体断流目标尚未完成。本次处理一小时长测中另行确认的恢复失败：车端服务重启需要数秒，App 原先仅在 0.5 秒后重试一次，连接被拒绝后一直离线，需要人工连接。

## 修改

`entry/src/main/ets/pages/Index.ets` 将已有有效实时视频连接的失联恢复扩展为一次有上限的恢复流程：最多 3 次，分别等待 0.5、2、4 秒。后续等待发生在前一次失败之后。首次启动和手动连接的失败不进入自动循环，三次失败后明确要求手动连接。新视频帧到达后结束当前恢复流程；下一次实际失联可以重新启动一次流程。

每次失联仍立即清空按键、停止续期、释放旧会话并停止旧预览。取消连接、页面隐藏和销毁仍会取消待执行重试；旧状态响应、旧帧和旧运动指令不能影响新连接。新画面到达之前禁止运动和调速，2 秒视频看门狗及车端运动租约未改变。增加连接失败原因、重试次数和间隔日志，以便区分无线停顿与服务重启。

## 离线验证

HAP 构建成功（HarmonyOS SDK API 23），已将签名调试包覆盖安装到本次 USB 手机。`tools/check-phone-control.cjs` 执行实际控制方法，新增早期服务拒绝后恢复、失败三次停止且手动失败不循环、后台取消后续待执行重试三项案例；该脚本及 `tools/check-camera-stream.cjs` 均通过。Git diff 空白检查通过。编译器仍有截图/图库等既有代码的异常处理和弃用提示，本次没有扩大修改这些模块。

接口参数、响应结构和视频协议没有改变；车端仍运行上一轮已部署的相机时间戳读取修复。没有重新修改车辆控制或模型文件，没有 Git 提交。

1. **13:26:42 开始，空闲小车受控重启服务。** 车端约 4.62 秒恢复。手机记录第 1 次等待 500 ms、第 2 次等待 2000 ms、第 3 次等待 4000 ms；前两次尝试被服务拒绝，第三次在 13:26:50.577 自动开启预览，13:26:51.591 开始重新输出 FPS 报告。未点击测试连接按钮，真实视频自行恢复。
2. **13:29:02 开始，空闲小车再次受控重启。** 在第 1 次恢复等待期间，13:29:04.413 实际进入后台，13:29:12.866 回到前台，同一 App PID 24476 保持。回到前台后继续观察 3 秒，没有后续重试、预览开启或解码报告；界面转储确认处于未连接状态，证明待执行恢复已取消。
3. 测试完成后通过连接面板手动恢复预览，手机又输出新解码帧。最后读取小车服务 active、相机 live，moving=false、controlBusy=false。本次没有发送运动命令，未测试实车运动和落地轮向。两次服务重启均是主动测试动作，不计入原长测的异常重启次数。

离线取消案例与真实后台/前台生命周期观察相互补充；没有把 Node 模拟结果当作真实手机测试。车端系统日期仍为 2024 年，具体时间以手机/电脑日志为准。
